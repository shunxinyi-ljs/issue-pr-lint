# issue-pr-lint

> 一个给 AI 编码助手用的 **GitHub Issue / PR 提交前审查** skill。

在文案发出去之前，逐条核对每个断言能不能指回证据——diff、测试输出、仓库代码。
防止"看起来很有道理、其实没验证过"的描述进入公开仓库。

---

## 它解决什么问题

AI 写 issue / PR 描述时，很容易写出这类句子：

> 配额耗尽的用户会看到"请充值"的提示，而不是"检查密钥"。

读起来通顺、方向也对。但**没人确认过前端到底显示什么**。
维护者如果去核对，发现不是这么回事，这个 PR 的可信度就没了。

这个 skill 做的就是：把文案拆成一条条可验证的断言，逐条问"证据在哪"。

---

## 什么时候用

| 场景 | 是否适用 |
|---|---|
| ✅ issue / PR 文案已写完，准备发布 | 适用 |
| ✅ 提交前想再确认一遍没有夸大或臆测 | 适用 |
| ❌ 还在调查、复现、写代码的阶段 | 不适用（没有文案可审） |
| ❌ 只是想让 AI 评价方案好坏 | 不适用（它只查证据，不判设计） |

## 怎么用

### Claude Code

```bash
# 1. 放到 skills 目录
mkdir -p ~/.claude/skills/issue-pr-lint
cp issue-pr-lint/SKILL.md ~/.claude/skills/issue-pr-lint/
```

然后直接说：

```
用 issue-pr-lint 审一下这个 PR
```

或者显式调用：

```
/issue-pr-lint
```

### 其他支持指令文件的工具

`SKILL.md` 本身是纯 Markdown，可以直接喂给任何能读系统提示的编码助手。

## 核心机制

### 1. 断言分级

文案里每句话都按证据强度定级：

| 级别 | 含义 | 处理 |
|---|---|---|
| **E1** | diff、命令输出直接支持 | 保留 |
| **E2** | 仓库代码、文档间接支持 | 保留，措辞留余地 |
| **E3** | 只能从上下文推理 | 降级为"待验证" |
| **E0** | 找不到任何依据 | 删除或提问 |

### 2. 降级前必须取证

**这是最重要的一条规则。**

判 E0 / E3 之前，必须先针对该断言做至少一次检索：grep 该值、读对应组件、查 changelog、找调用方。
"我没看过"不等于"没有证据"——证据通常就在仓库里。

报告里必须说清楚找过什么，只说"没证据"不算通过。

### 3. 不删用户价值陈述

以下内容**不允许因为"缺直接代码证据"而删除**，只能改为"待核实"：

- 用户可见行为的变化
- 错误信息 / 提示文案
- 修复后用户该做什么

这些是 issue / PR 的价值主张。误删的代价大于保留。

### 4. 跨模块影响必查

改动涉及错误码、状态值、默认值、API 字段时，必须 grep 该值的**所有**引用，逐条确认下游能否处理新取值。

> **典型陷阱**：只看离改动最近的那张映射表就下结论。
> 同一个值往往有两张表——一张管字段内联提示，一张管结果展示。

### 5. 反向验证（可选）

对 PR，可以临时撤下修复、保留新增测试，确认测试确实转为失败，再恢复。

这能证明"测试守护了这个修复"不是一句空话。

## 输出格式

固定四段：

```
## 终稿
（可直接粘贴的正文）

## 待确认清单
- [必须补] ...
- [建议补] ...

## 改动摘要
- 删除：...
- 措辞降级：原"已修复" → "本 PR 修复"

## 提交命令（不自动执行）
gh pr create --title ... --body-file ...
```

---

## 它不做什么

- **不提交、不推送、不改代码**。生成的 `gh` 命令只展示，由人执行。
  （唯一例外：反向验证，需用户批准，且必须恢复原状。）
- **不判断方案好坏**。它只查"你的说法有没有根据"，不评价"你的修复是不是好设计"。
- **不发现代码 bug**。它审的是文案与证据的对齐，不是实现正确性。

## 一次真实翻车（写这个 skill 的原因）

审查一个改了错误码的 PR 时，流程是这样走的：

1. PR 正文写着：「配额耗尽的用户会看到"请充值"的提示，而不是"检查密钥"」
2. skill 规则说：无证据的断言要删
3. 审查者（AI）想：「我没看过前端 UI」→ 判定 E3
4. **准备删除这句话**

但实际去读前端代码后发现——文案原原本本在那里：

```javascript
// ModelSettings.tsx:2023
insufficient_balance:
  "模型账户余额不足；充值或换 key 后再检测，会自动接着处理",
```

**差一点删掉 PR 里唯一一句说明用户价值的话。**

这件事直接催生了硬规则 6 和 7：**降级前必须取证**，**不删用户价值陈述**。
