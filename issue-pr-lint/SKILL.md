# Issue / PR 提交前审查

## 适用前提

这个 skill 是交付前的**审查与改写**，不是文案生成器。触发时用户已经完成定位、修复和验证，文案也已写完或写完草稿。你的任务是：核对事实 → 对齐结构 → 做减法 → 输出终稿和待确认清单。

如果用户还没完成工作（只有想法、还没定位、还没验证），直接说明不适用，回到正常工作流。

## 何时调用

**草稿正文写完之后、提交之前。** 输入是「已完成的改动 + 已写好的文案」，输出是「终稿 + 待确认清单」。

调用前必须同时满足：

1. 改动已经 commit（或至少 `git diff` 可见）
2. 验证已经跑过，有命令输出
3. **草稿正文已经写出**（哪怕是粗糙的初稿）

三条缺任意一条，说明不适用，回到正常工作流。

三种输入形态，按实际情况选取核查项：

- **A 只有 issue**（无代码改动）：跳过 PR 相关核查，重点在现象、复现、期望 vs 实际、环境。
- **B 只有 PR**（改动已存在）：重点在动机、范围、验证证据、破坏性变更。
- **C issue + PR 同一会话**：全量核查，额外核对 PR 是否回应了 issue 的每一条诉求（做法见第三步第 4 项）。

缺信息时提问或列入待确认，不要补全。

## 硬规则（违反即失败）

1. **禁止新增事实**。原文没有的版本号、环境、性能数字、测试结论、影响范围，一律不得出现在终稿里。
2. **证据优先于文采**。每一句陈述句都必须能指回 diff、命令输出、仓库文件或原文。
3. **减法优先于加法**。默认动作是删和压，不是补充章节。
4. **审查优先于重写**。原文结构基本可用时只做局部修改，并说明改了什么。
5. **不确定就停下**。无法核实的断言不得改写成更肯定的说法，只能降级为推测或列入待确认。
6. **降级前必须取证**。把任何断言判为 E0/E3 之前，必须先针对该断言做至少一次检索或读取：grep 该值/枚举/函数名、读对应组件或配置、查 changelog 或 git log、找调用方。"我没看过"不等于"没有证据"——证据通常就在仓库里，读一行就够。取证后仍找不到，才允许降级。
7. **不删用户价值陈述**。以下内容不得因"缺直接代码证据"而删除，只能改为"待核实"并列入待确认清单：用户可见行为的变化、错误信息或提示文案、修复后用户该做什么。这些是 issue/PR 的价值主张，误删的代价大于保留。
8. **不执行任何写操作**。不提交、不推送、不改工作区、不回滚代码。生成的 `gh` 命令只展示。唯一例外是第三步第 2 项的反向验证：允许临时撤下修复再恢复，但不得产生新 commit、不得推送，结束后必须回到原状。

## 第一步：收集证据

按需读取，不要全量扫仓库：

- 改动：`git status --short`、`git diff --stat`、`git diff HEAD`。分支场景用 `git diff $(git merge-base origin/HEAD HEAD)...HEAD`；取不到时退回 `git log --oneline -10` 加 `git diff HEAD~1`。
- 验证记录：本会话实际跑过的测试或复现命令及其输出。没跑过就记为"未验证"，不能假定通过。本会话没有验证记录时（例如跨会话、跨 agent 使用），先向用户索取输出或询问是否重跑，不要直接把全部断言标为 E3。
- 仓库约定，按顺序找，命中即停：`CONTRIBUTING.md` → `.github/CONTRIBUTING.md` → `docs/CONTRIBUTING.md` → `.github/ISSUE_TEMPLATE/*.yml|md` → `.github/PULL_REQUEST_TEMPLATE.md` → `.github/pull_request_template.md` → `docs/pull_request_template.md`。
- 关联对象：文案引用的 issue/PR 编号，用 `gh issue view <n>` / `gh pr view <n>` 读取。
- 重复检查：`gh issue list --search "<关键词> in:title" --state all`、`gh pr list --search ...`，只报"疑似重复"，不下结论。

## 第二步：把文案拆成断言清单

逐句扫描。凡出现下列词即视为可验证断言：

- 中文：导致、崩溃、报错、失败、修复、解决、只影响、不影响、兼容、默认、首次、全部、唯一、性能、无破坏性变更、已测试。
- 英文等价：causes、crash、throws、fails、fixes、resolves、only affects、does not affect、compatible、by default、first、all、every、only、performance、no breaking changes、tested、verified、guaranteed、never、always。
- 元规则：任何含数字的比较或性能声明（"提升 30%""减少一半"）、任何版本号断言（"自 v2.3 起""在 1.x 不存在"），无论是否命中上述词表，一律视为可验证断言。

给每条断言定级：

| 级别 | 含义 | 能否写进正文 |
|---|---|---|
| E1 | diff、命令输出直接支持 | 可以 |
| E2 | 仓库代码、文档、已合并 PR 间接支持 | 可以，措辞留余地 |
| E3 | 只能从会话推理得出 | 不可以，降级为"推测/待验证" |
| E0 | 原文有、但找不到任何依据 | 删除或提问 |

内部维护清单：`断言 | 位置 | 证据 | 级别 | 处理`。最终报告只给结论，不铺整张表。

## 第三步：专项核查

**1. 问题是否真实存在（issue 侧）**

- 会话里有复现记录吗？有就核对复现步骤与记录是否一致（命令、参数、环境）；没有就标"未复现"，不许写"可稳定复现"。
- 现象描述是否具体到可搜索：错误信息原文、触发条件、版本。
- 期望与实际是否成对出现，缺一半就是结构问题。

**2. 修复是否真的针对该问题（PR 侧）**

- 可机械核对的部分：diff 是否触及文案声称的根因位置；新增测试是否覆盖改动的分支；是否夹带无关文件（lock、格式化、重命名、无关重构）。
- 测试有效性：**必须**做一次反向验证（临时撤下修复，确认测试转为失败，再恢复）。这是唯一能证明"测试真的覆盖了修复"的手段，跳过它等于放弃验证。只有用户明确拒绝时才跳过，并记为"未做反向验证"。
  - 执行约束：不得产生新 commit、不得推送；优先用非破坏手段（临时 worktree 复制测试文件到未修复代码上、反向应用补丁、`git stash push -u -m "<唯一标签>"`），不使用 `git reset --hard`、`git checkout .` 这类会丢改动的命令；验证后必须恢复，并用 `git status --short` 确认与开始时一致。
  - **必须区分两类用例**：反向验证后，把新增用例分成「在未修复代码上失败」和「在未修复代码上仍然通过」两组。
    - 前者才是**修复验证**，计入证据，写进 PR 正文的变异验证一栏。
    - 后者是**护栏用例**（反向用例、边界用例、其他方言/其他路径的覆盖），本来就不该在未修复代码上失败，不能计入"测试证明了修复有效"的证据。
    - 常见陷阱：8 个新用例里只有 4 个真正验证修复，另外 4 个是 fake-cursor 或其他路径的护栏。若在正文里笼统写"新增 8 个用例全部通过"，维护者会误以为 8 个都是端到端验证。
  - 无法执行反向验证时（如依赖外部服务不可达），读测试代码判断断言是否覆盖失败路径；判断不了就写"测试有效性未被证明"，不得含糊表述为"已测试"。
- 需人判断的部分（根因是否唯一、边界条件、是否权宜之计）：不下结论，只写"现有证据支持到哪一步、还缺什么"。
- 声明范围与实际范围：文案写"只改 X"，用 `git diff --name-only` 对；不一致就要求改写或拆分。

**3. 破坏性变更与风险**

- 逐项检查 diff 是否涉及：公开 API 签名、默认值、配置键名、CLI 参数或输出、序列化格式、错误码、权限或安全行为。
- 涉及就必须在正文明确写出；不涉及才允许写"无破坏性变更"。
- 敏感信息扫描：密钥、token、私钥、内部域名、绝对路径（`C:\Users\...`、`/home/...`）、邮箱、客户数据。发现即要求脱敏，并指出位置。

**3b. 改动的值是否被其他模块消费（必查）**

文案里一旦出现"错误码""状态值""默认值""API 字段"这类**被下游读取的值**，必须在仓库里搜索该值的所有引用，逐条确认下游能否处理新取值：

- 错误码 / 枚举 / 状态值 → 前端文案映射表、契约测试、API 文档
- 默认值变更 → 文档、示例、迁移脚本
- API 签名或字段 → 调用方、序列化层

做法：`grep -rn "<新取值>\|<旧取值>" <相关目录>`，对每处命中判断"新值会不会落进未覆盖的分支"。

**这一步的典型陷阱**：只看离改动最近的那张映射表就下结论。同一个值往往有两张表——一张管字段内联提示、一张管结果展示，只查一张会得出"下游没处理"的错误结论。

**3c. 改动的代码路径当前是否可达（必查）**

改动的逻辑再正确，如果它所在的路径在生产中被关闭，文案就不能声称"修复了线上问题"。必须先确认可达性，再决定措辞。

做法：搜索 feature flag、开关、环境变量、编译期常量，确认改动所在分支当前是否被执行：

```bash
grep -rn "ENABLED\|FEATURE_\|_FLAG\|if False" <改动所在模块>
grep -rn "<改动所在的方言/后端/模式名>" <配置与入口文件>
```

判断与措辞：

- **可达**（走默认路径）→ 可以写"修复了 X 问题"。
- **不可达**（被开关关闭、后端未启用、平台分支不生效）→ 正文**必须主动说明**"当前不可达，为将来启用做准备"。这既诚实，也避免维护者认为作者不了解现状。
- **不确定** → 列入待确认清单，不得默认可达。

**这一步的价值**：维护者判断作者是否做过功课，第一眼看的就是这里。声称修复了一个被开关关闭的路径上的 bug，会直接损失可信度；主动说明反而加分。

**4. issue 诉求逐条回应（仅 C 型）**

- 从 issue 正文提取诉求清单，每个"期望"单独算一条。
- 逐条标注由 PR 的哪个改动、哪条测试或文案中的哪句话回应。
- 没有回应的诉求进待确认清单，由用户决定补回应还是声明超出范围。
- 核对 PR 正文的关联关键词：完全回应 issue 时用 `Fixes #<n>` / `Closes #<n>`；只回应部分诉求时改用 `Refs #<n>`，并在正文说明剩余范围。

## 第四步：对齐结构

- 仓库有模板：严格按模板的章节名和顺序填，不新增章节。章节缺内容时：必填章节列入待确认清单，可选章节整节删掉，都不写"无"。
- 仓库无模板：用最小集。
  - issue（bug）：现象 → 复现步骤 → 期望 vs 实际 → 环境 → 影响范围
  - issue（feature）：要解决的问题 → 期望行为 → 现有替代方案及不足
  - PR：一句话结论 → 改动内容 → 验证方式 → 风险/破坏性变更 → 关联 issue
- 一节一事：每节只回答一个问题。
- 首屏三行：标题加前三行必须能回答"做了什么、为什么、影响谁"。
- 标题：包含可搜索的关键标识（错误码、函数名、模块名、场景），不写"修复了一个问题""优化某功能"。
- 术语统一：同一概念全文一个词，优先沿用仓库用词。

## 第五步：做减法

按顺序删，删完再压：

1. 过程噪声：调试过程、失败尝试、临时假设、中途结论。
2. 空话：全面、优雅、健壮、显著提升、大幅优化、彻底解决。
3. diff 复述：不逐文件罗列。需要指路时给"重点看这 2-3 处 + 为什么"。
4. 过度承诺：永久修复、彻底避免、完全兼容，除非有 E1 证据。
5. 指责性表述：维护者应该、显然是、居然没有。
6. 冗余背景：维护者能从代码直接看出的内容，不重复解释。

**减法禁区**：用户可见行为的变化、错误信息/提示文案、修复后用户该做什么——这些不进删除清单。没有直接证据时改为"待核实"并写进待确认清单，不直接删（见硬规则 7）。

长度预算：issue 正文 ≤ 300 词（中文约 600 字）；PR 正文 ≤ 400 词（中文约 800 字）。模板必填字段不受预算约束；其余内容超出时输出压缩版，压缩优先删解释、保留证据。

## 第六步：输出

固定四段，顺序不变。语言跟随原 issue/PR 的语言。

输出前对照"通过标准"逐条自检，任何一条不满足时先修正再输出。

```
## 终稿
<可直接粘贴的正文，不含批注、方括号占位、审查说明>

## 待确认清单
- [必须补] ... —— 缺什么证据，影响哪句表述
- [建议补] ...
（没有则写"无"）

## 改动摘要
- 删除：...
- 重排：...
- 措辞降级：原"已修复" → "本 PR 修复"，原因：无 E1 证据
（只列影响事实表达的改动，不列错别字）

## 提交命令（不自动执行）
<gh issue create / gh pr create 命令，标题与正文使用终稿>
```

终稿里不得出现 `[TODO]`、`<!-- -->`、"（待补充）"、"根据你的描述"这类内容。

正文较长时，`gh` 命令优先用 `--body-file`：经用户同意后把正文写到仓库外的临时文件，用完即删；短正文用内联方式。

## 二次审查

用户改完再跑一次时，只输出：仍未解决项 + 剩余待确认项 + 是否通过。不要整篇重出，也不要提新的改写建议，除非首次遗漏了硬规则违规。

## 通过标准

- 终稿中每个陈述句都能指回证据，或已降级为推测/待确认。
- **每条被降级的断言，报告里能说清取证动作**（搜了什么、读了哪个文件）——只说"没证据"而不说"找过什么"不算通过。
- **改动涉及错误码/状态值/默认值时，已列出该值的下游引用并逐条确认**（第三步 3b）。
- **已确认改动所在路径当前是否可达；不可达时正文已主动说明**（第三步 3c）。
- **已做反向验证，并区分了「修复验证」与「护栏用例」两类新增测试**（第三步第 2 项）；未做时已写明原因。
- 结构符合仓库模板；无模板时符合最小集。
- 无过程噪声、无空话、无逐文件 diff 复述。
- 待确认清单里的每一条，用户都能直接判断"补还是不补"。
- 未执行任何写操作。
